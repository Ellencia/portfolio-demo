# 최종 산출물 검수

기존 데모의 평가와 최종 전달에 사용한다. 정지 카드, 웹 재생, MP4는 서로 다른 검수 대상이다. 아래 모든 항목을 모든 작업에 기계적으로 적용하지 말고 요청한 형식과 변경 범위에 맞춘다.

## 1. 사실과 산출물을 맞춘다

- 검사한 URL·파일명과 버전 또는 수정 시각을 기록한다. 캐시나 오래된 영상을 보고 새 수정이 반영됐다고 보고하지 않는다.
- PDF·홈페이지·개별 데모·영상에서 사용자 수, 처리 범위, 상태, 수치가 서로 다르면 최신 사실을 확인한다. 하나에 맞춰 임의로 덮어쓰지 않는다.
- 실제 앱, 예시 데이터, 재현, 설명용 결과의 표시가 각 장면에서도 보이는지 확인한다.
- 시험 조건과 미검증 범위가 주장 바로 옆에서 이해되는지 본다. 성공한 입력 사례만으로 무응답·거부·잘못된 입력까지 처리됐다고 말하지 않는다.
- 원본 촬영 자료와 음원의 사용 범위를 확인한다. 곡의 작곡 시기만으로 특정 편곡·녹음·악보 판본의 사용 권한을 추정하지 않는다.

## 2. 이해 검수

가능하면 작업 과정을 모르는 사람이 최종 화면만 보게 한다. 외부 평가를 할 수 없으면 처음 보는 사람의 입장에서 검토하되, 이를 실제 사용자 테스트로 보고하지 않는다. 다른 모델의 답도 사람의 사용성 검증과 구분한다.

다음 질문 중 장면에 맞는 것을 고른다.

- 무엇이 불편해서 이 도구를 쓰는가?
- 무엇을 입력했는가?
- 도구가 무엇을 했고 결과는 어떻게 달라졌는가?
- 사람이 판단하거나 눌러야 하는 지점은 어디인가?
- 실제 결과와 설명용 예시 중 무엇을 보고 있는가?

답이 나오지 않는다면 먼저 맥락·대응 관계·화면 크기를 살핀다. 설명 문단을 추가하는 것으로만 해결하지 않는다. 객관식 평가를 사용했다면 보기 순서나 질문의 모호함도 확인하며, 오답을 곧바로 데모의 결함으로 단정하지 않는다.

## 3. 화면과 재생 검수

**대상 기기 크기에서 정상 속도로 본다.** 썸네일만 보고 작은 글자를 읽을 수 있다고 판단하지 않는다. 프레임 검수와 정상 속도 검수는 목적이 다르다.

- 정보가 다 나온 뒤 읽을 시간이 있는가? 다음 카드가 앞의 정보를 너무 빨리 덮지 않는가?
- 비교할 원문과 결과가 함께 남는가? 보고 영역을 지웠다 다시 만드는 바람에 맥락이 끊기지 않는가?
- 제목·핵심 결과는 충분한 대비로 보이는가? 흐린 글자, 박스 밖 잘림, 크기가 튀는 카드가 없는가?
- 진행 표시가 전환·재생 반복 후에도 남는가? 이전·다음·정지·재생의 실제 동작이 표기와 맞는가?
- 스틸 이미지에서는 설명이 없어 보이는데 영상에서만 보이는지, 반대로 영상에서 너무 짧게 스치는지 확인했는가?

화살표와 로딩 동작을 바꾼 경우에는 해당 구간을 느리게 보거나 프레임으로도 확인한다.

- 화살표 출발·도착점이 대상에 붙는가? 끝난 뒤 점이나 선 조각이 남지 않는가?
- 도착 방향과 곡선이 시선을 자연스럽게 이끄는가? 다른 문장이나 박스를 가리지 않는가?
- 로딩 요소가 겹치거나 굵기·길이가 갑자기 변하지 않는가? 가속·감속에 불연속이 없는가?
- 회전 시작 위치나 화살표 각도처럼 사용자가 구체적으로 정한 값은 그 값으로 확인한다. 특정 장면에서 요청된 각도·속도 비율을 모든 데모의 기본값으로 일반화하지 않는다.

## 4. 음향 검수

음향이 있는 경우 **최종 인코딩된 영상의 소리**를 듣는다. 소리를 직접 확인할 수 없다면 확인하지 못했다고 명시하고, 파형·코드 검사만으로 청취 완료라고 쓰지 않는다.

- 요청한 악기·파트가 실제로 들리는가? 멜로디가 반주에 묻히거나 효과음이 음악·내레이션을 덮지 않는가?
- 원곡의 마디, 악보의 마디, 녹음의 시작점, 영상 타임코드를 혼동하지 않았는가?
- 시작 위치를 바꿀 때는 예를 들어 `총보의 지정 마디 → 원본 음원 시각 → 최종 영상 시각`의 대응을 확인한다. 기준이 모호하면 추정해서 재렌더하지 말고 확인한다.
- 반복과 끝부분이 어색하게 끊기지 않는가? 볼륨이 튀거나 음이 겹쳐 의도와 달라지지 않는가?
- 정량 음량·클리핑 검사는 보조 증거다. 실제 파트 구성이나 음악적 자연스러움을 대신 판정하지 않는다.

## 5. 변경 검수와 전달

1. 요청한 변화와 관찰 가능한 완료 조건을 적는다.
2. 실제 전달할 형식으로 다시 출력한다. 영향을 받는 캡처·영상·사이트 복사본을 확인한다.
3. 변경 구간뿐 아니라 직전·직후 전환, 반복 시작·종료처럼 영향을 받는 부분을 재생한다.
4. 확인한 파일·구간·결과를 기록한다. 실패나 미확인은 숨기지 않는다.

검수 기록은 다음처럼 짧게 남길 수 있다.

| 대상·버전 | 요청한 변화 | 실제로 확인한 것 | 남은 확인 |
| --- | --- | --- | --- |
| 최종 MP4의 수정 장면 | 새 카드의 읽는 시간 확보 | 정상 속도 재생에서 앞 카드가 남고 다음 카드가 뒤에 등장 | 별도 관람자 이해 평가는 미실시 |
| 웹 재생본의 해당 전환 | 화살표 끝 잔상 제거 | 전환 직후·다음 장면·반복 재생에서 잔상 없음 | 없음 |

위 표는 기록 방식의 예시다. 실제 관찰 없이 그대로 완료 보고에 붙이지 않는다.

완료는 “코드를 바꿈”이 아니라 “전달할 산출물에서 요청한 변화가 확인됨”이다. 배포가 포함되면 원격 파일과 링크도 확인한다. Git 변경이 원격에 올라간 것과 GitHub Pages 같은 서비스의 배포 완료는 구분한다.
